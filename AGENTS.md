# Development Guide

## General Principles

- Keep changes focused on their purpose and follow the existing design and naming conventions.
- Include related documentation in the same change as the implementation.
- Confirm unclear specifications or changes with a broad impact before starting work.
- If work stops before reaching the intended completion point, clearly report why it stopped, what has been completed, and what must happen next.
- Conduct all communication in Japanese.
- While communicating in Japanese, write in-app text, comments, and identifiers in English.
- Write all in-app text in English.
- However, write documents generated by SpecKit in Japanese.
  - Take particular care because `tasks.md` can easily remain in English when it is created.
- Submitted documents use the English version as the canonical source. When a Japanese version is also provided, name it `*_ja.md`; use the corresponding `*.md` filename for the English version.
- When a SpecKit agent-context update occurs, update the content between `<!-- SPECKIT START -->` and `<!-- SPECKIT END -->` to reference the latest `plan.md` for the applicable SPEC. If the automated update cannot run, update it manually.
- If escalation is required, escalate without considering detours or alternatives.
- Avoid Python when the task can be completed without it. If Python software must be installed, do not install it directly into the system; use a venv virtual environment.

## Spec Implement Workflow

- Complete every unfinished item in the applicable Spec's `tasks.md`.
- However, stop development and testing if there are questions or problems.
- Because interim reports stop the work, do not report until completion. Review this request before sending what would be the final response.
- Perform manual testing together after all implementable work is complete.

## Quality

- Verify changed behavior with appropriate tests.
- If tests cannot be run, share the reason and what remains unverified.
- Run configured formatters and linters.

## Git

- Do not overwrite or delete other people's changes.
- Keep commits small and use messages that explain the reason for each change.
- If `gh` returns an authentication, keyring, or `api.github.com` connection error in Codex's restricted execution environment, retry the same check once in an escalated environment before asking the user to reauthenticate.
  - If a write operation using `gh` fails, use a read command to check whether the target, such as a PR, was already created or updated before retrying so that the operation is not duplicated.
  - Ask the user to run `gh auth login` only if `gh auth status` also fails in the escalated environment.
- When setting a body with `gh pr create` / `gh pr edit`, never use `--body`; always use `--body-file` to prevent broken line breaks.
- Procedure:
  1. Write the body to a temporary Markdown file (for example, `/tmp/pr_body.md`).
  2. Run `gh pr create --body-file /tmp/pr_body.md` (or `gh pr edit --body-file /tmp/pr_body.md`).
  3. Run `gh pr view --json body --jq .body` to verify that line breaks were preserved.

## Testing Policy

- As a rule, add tests for functions that can be unit tested. In particular, test fixed contracts, decisions with many branches, and boundary conditions in pure logic.
- Add utility-function tests only for reusable pure functions or functions with enough branching that integration tests alone make failures difficult to isolate.
- As a rule, do not add individual unit tests for thin wrappers, simple delegation, or functions that only connect external-library calls (unless they contain processing of their own).
- Prefer unit tests for layers close to the source of truth, such as repositories, stores, and schemas. Cover flows that cross MCP connections or multiple layers with integration tests.
- Cover UI state branches and important display transitions with unit tests, and supplement final flow verification with quickstarts or manual tests.

## Codex Usage Log

- When Codex is used for planning, design, implementation, research, issue resolution, or important decisions, update `USE_CODEX.md` before completing the work.
- Create a heading for each date and record the exact model name used and the work performed as bullet points.
- Do not record simple checks, casual conversation, or answers to questions that make no content changes.
